# 审阅项目结构

评估实用性，而非是否符合模板。默认保留已经支持正确工作的结构。

## 1. 确定审阅边界

确认项目根目录、用户想解决的工作问题及允许读取的范围。若任一项不清楚，扫描前只问最小必要问题。

明确说明本次审阅只读。即使明显存在缺陷，也不得创建、编辑、重命名、移动、删除或更新 Memory、索引或项目状态。

## 2. 按正确顺序阅读证据

在获批准范围内，只检查能回答所述问题的内容。

1. 从根目录文件及用户点名的入口/状态文档开始。报告中写明它们的精确路径。
2. 根据证据识别项目类型：
   - **目标导向型**：有可定义的结果或终点；寻找一个当前进度/状态位置。
   - **运营型**：重复开展的工作、没有单一终点；寻找最小有用的并行状态，如队列、审阅节奏、决策日志或活跃事项列表。
3. 只沿入口点名的材料路径，或解决所请求工作问题所需的路径继续读取。

分类项目自身的生命周期，而非某一个待办清单或临时事项的形式。一个长期业务中枢即使每个事项都有里程碑，只要其中包含多个倡议、周期工作或持续队列，仍属于运营型。若证据同时支持有限交付与持续运营，要说明混合边界，并判断状态位置是否安全地服务两者；不得只因存在任务列表就强迫归为目标导向型。

除非用户明确指定，不要把嵌套的 `test`、`测试`、`fixtures`、`examples`、`archive`、`归档`、供应商提供、生成或第三方目录视为活跃项目结构的证据。不得把缺少某个偏好文件名推断为缺陷。

## 3. 用真实续接检验结构

基于可用证据回答：

1. Agent 能否发现从何处开始，以及项目的用途？
2. 它能否区分当前事实、稳定规则、历史材料与未验证草稿？
3. 它能否以适合项目类型的方式识别当前状态和下一项安全行动？
4. 它能否仅在需要时，经由明确路径加载详细材料？
5. 每项当前事实是否有唯一权威归处，或有明确标记的冲突？
6. 结构是否说明相关写入、隐私或范围边界？
7. 是否存在实用的会话结束更新或交接做法？

将不可用或冲突的证据视为**无法判断**。不要把未知写成“未开始”“无人负责”或“缺失”。一份文档可以是旧参考资料，而不代表整个项目有缺陷。

## 4. 报告 Keep / Change / Ignore

给出简洁分类、实际检查过的路径及下表：

| 结论 | 证据 | 影响 | 建议 |
|---|---|---|---|
| Keep | 精确路径和观察到的行为 | 为什么它支持正确续接 | 保持不变 |
| Change | 精确缺口或冲突 | 对工作、安全或续接的具体影响 | 最小改动建议；等待确认 |
| Ignore | 不是当前问题的观察 | 为什么不应行动 | 不行动 |

只有当改变的收益有证据支持，且小于维持现状的成本时，才报告 Change。优先更新既有权威文件，而非创建新看板、数据库或通用模板。将过时的当前状态与健全的稳定入口区分开。

不要仅因项目不同于本 Skill 的术语或文件命名而提出改变。对于成熟、可续接的结构，“Keep / 无需改变”是完整且理想的结果。

## 5. 安全收尾

说明最小下一步行动。用户若希望执行任何拟议 Change，展示精确目标路径、拟议编辑和对事实来源的影响，然后移交 `launch-project` 的最小修复流程另行确认与执行；本 Skill 仍保持只读。修复完成后的新会话续接检查属于该执行流程或另一个明确请求，不属于本次 Review。
