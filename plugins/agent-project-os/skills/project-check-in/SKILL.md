# 项目检视

将今天的工作转为下一项安全行动，且不创建第二套项目事实。保持范围狭窄：用项目稳定契约与当前运营状态理解用户更新，然后为下一会话留下简短、已确认的交接。

## 1. 确定项目边界

确认项目根目录和允许读取的文件或文件夹。用户提供具体项目路径且已授权该项目时，以其为读取边界；否则遵循下方**边界尚未建立时的回应**。

- 只读取项目契约/稳定入口及它点名的当前运行状态产物。只有理解这次特定更新所必需时，才沿额外材料路径读取。
- 说明读取的精确路径。不得扫描同级项目、整个工作区、归档、聊天或全局 Memory。
- 项目证据强于记忆中的对话。没有支持证据的主张标为**用户陈述 / 等待确认**，不得写成既定事实。
- check-in 期间不得创建缺失的契约、状态文件、日报或模板。

### 边界尚未建立时的回应

缺少项目路径只阻止读取与写入，不阻止帮助。用户描述真实情况却未指明项目时，不能把“给我路径”作为回复的唯一内容。

同一回复中：

1. **基于用户实际所说采取行动。** 只依据其说法和已声明限制（如可用时间、期限或超支），给出一项现在可执行的具体行动。无需项目证据、用户可以直接采用的通用方法在此是合法的。
2. **标明依据。** 明说建议来自其描述，尚未与项目文件核对。其报告的每项事实都保持为**用户陈述 / 等待确认**。
3. **将路径作为次要问题。** 请求路径以便下一轮有据可依，而非作为本轮行动的前提。

没有读取边界时：不得提议状态更新；第 5 节的收尾提议不适用，未确认路径或虚构目标都不可替代。第 3 节第 4 项仍保留，但只写一句“确认项目路径前不提议状态更新”。不要读取项目文件、索引、归档或 Memory 来弥补路径缺失；不要把任何建议、估计或诊断说成既定项目事实，也不得推断工作未开始、已完成、无人负责或受阻。

第 4 节的升级测试在此仍适用，但将其中“证据”理解为用户陈述并如此引用。触发时，在 check-in 之外提供中途审阅作为可选项；不得用它替代 check-in，也不得在用户考虑审阅时扣留即时行动。未触发时，完全不要提起审阅。此时暂停第 2 节的 Skill 建议：选择 `launch-project` 或 `review-project-structure` 需要知道项目成熟度，不能在此推断；请改问路径。

## 2. 只恢复当前所需上下文

尽可能找到：项目目标、范围、角色、隐私/写入边界和材料路径；当前阶段/周期、已确认事实、下一步、开放决定、阻塞和待补全上下文；以及只与本次更新有关的来源（如点名的决定、交付物或当前队列项）。

若契约或当前状态产物缺失、不完整、冲突或不在批准范围，精确说明无法恢复什么。只问帮助当前更新所需的最小事实。不得推断工作未开始、已完成、无人负责或受阻。

若缺失产物阻止的是安全续接而不仅是本次回答，结构不足的项目推荐 `launch-project`，成熟项目推荐 `review-project-structure`。保持该建议只读；不得在此 Skill 中启动或重组。只有读取边界存在时本段才适用。

## 3. 处理更新

在不扩展为通用项目访谈的前提下分类用户输入：

| 更新类型 | check-in 回应 |
| --- | --- |
| 进展或已完成工作 | 识别改变、剩余内容和最小下一步。 |
| 阻塞或延误 | 分开已确认阻塞、缺少证据和所需决定；提出解除阻塞行动。 |
| 决定或变化的约束 | 说明项目影响和最小受影响状态项；不得悄悄覆盖早先决定。 |
| 新事实或观察 | 标明来源与置信度；识别是否改变当前计划。 |
| 今天计划请求 | 使用当前状态和已声明的可用时间/限制；不得虚构优先级或截止日期。 |

一次更新可匹配多行。必须在单一回复内处理所有匹配行，不得遗漏其中任一项，也不得因此分成多轮。保留每一项用户陈述事实的信息形态：数字未说明单位、货币、分母或范围含义时，保持无单位并标记缺失项；开放决定保持开放，提到的人、选项或示例除非用户明确说明，否则不是穷尽候选，不能将“谁决定？”缩为更新中提到的人之间二选一。

没有读取边界时，所有行同样适用，但只能从用户已述情况和限制出发，标明该依据，且不得点名任何受影响项目状态项。某行要求最小受影响状态项时，说明待路径明确后可能需要更新什么，不能断言。

返回简洁 check-in：

1. **我的理解**：用户陈述的更新、有依据的项目上下文和不确定性。没有读取边界时，明确未读项目文件，并将“有依据的”部分留空，不能用推断填充。
2. **本次会话下一步行动**：准确一项现在可做的具体行动。它可包含多个步骤，只要是同一行动；不列出让用户选择的备选项。只有该行动受阻时才加一个范围狭窄的问题。
3. **关注 / 决定**：仅列需留意的实质依赖、风险或负责人决定。
4. **拟议状态更新**：供后续会话续接所需的最小精确改动，含目标路径、拟议文本或替换、每项新事实来源，以及足以让新会话识别已确认事实、开放项、下一步和边界的信息。没有读取边界时，保留此标题并只放一句“确认项目路径前不提议状态更新”。此处绝不能放占位、推测或虚构内容。

不要把建议、预测或 Agent 诊断写成已确认项目事实。重复运营更新留在项目既有运营记录中，不能仅因每日更新就新建平行日记。

## 4. 升级但不过度介入

证据显示以下任一情形时，推荐**只读中途审阅**：目标、范围、成功标准、负责人或决策边界已变更或与项目契约冲突；同一阻塞、失去节奏或变通方案反复出现，当前下一步不再能解决；多个当前事项之间必须权衡优先级、资源、假设或策略；用户明确询问是否保留、改变、暂停或重规划工作。

解释触发原因及证据，并提出对目标、范围、节奏、阻塞和策略的只读审阅。审阅只是可选项，不能替代：仍要给出本次会话的下一步行动，避免用户等待审阅决定。只有用户改为要求审阅时，才省略 check-in 自己的下一步。除非用户后来确认具体变更，不要写入重规划、修订契约或把审阅结论提升为事实。

涉及敏感个人、健康、儿童、客户、人事、财务或私密信息时：使用最小必要摘要，避免复述标识符和不必要细节；保留在获批准项目范围内，绝不提议用于工作区 Memory、Portfolio 或外部行动；区分实际支持与医疗、法律、学校、心理健康等专业决定，必要时提示需合格专业人士或所有者决定；用户未明确要求保存时，记录前先询问。

## 5. 提议后等待，再改变状态

每次已有读取边界的 check-in，都以最小状态更新提议收尾。它可以添加已确认结果、替换下一步、记录阻塞、解决一项待补全上下文，或仅当既有项目设计要求时新增带日期的运营条目。边界尚不存在时，服从第 1 节：给出帮助，不提议任何内容。

在用户明确确认目标与拟议内容两者前：不得创建、修改、移动或删除项目文件；不得更新工作区 Memory、索引、Portfolio 记录或无关项目文件；不得声称项目已更新。

确认后，重读已批准目标，只应用已确认的最小改动，并报告精确路径和变更。保留冲突及未确认主张原状。写入后说明下一次续接点。

## 护栏

- 常规更新中不要重新进行项目启动访谈。
- 不要用最近聊天消息替代缺失的项目契约或当前状态。
- 不要扩展已批准范围来寻找更方便的答案。
- 不要替用户诊断、决定、发送、安排、报名、发布或采取其他外部行动。
- 不要创建第二个项目事实来源，也不要将每日动态提升为长期 Memory。若出现稳定的跨项目学习，只能作为候选交给 `bootstrap-workspace`，且附项目来源、适用范围及确认或最近审阅日期。
