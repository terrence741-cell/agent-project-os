# 初始化工作区

为 Agent 工作区建立一个小而可信的定向层。目标不是收集一切，而是在不将私密材料、临时状态或未解决冲突复制进 Memory 的前提下，保留稳定规则和有用的路由信息。

## 1. 先设定边界

读取文件前，确定：

- 用户希望工作区达成什么目标；
- 允许读取的精确文件夹或文件；
- 不得读取或写入的区域；
- 本次是只读，还是可以在稍后提出写入建议。

范围不清楚时，问一个简短澄清问题。默认只读。用户即使说“整理”，也不得因此扫描整个工作区。

## 2. 仅盘点获授权的定向来源

从最小有用集合开始：指定的 Memory 文件、项目索引、工作区入口，以及已列出项目的标题或 frontmatter。保留精确的来源清单。

除非用户明确纳入，不要读取项目正文、归档、聊天记录、凭据或个人/私密文件夹。不得把文件名或推断出的惯例当作证据。

目标 Memory 的路径和组织方式同样属于用户边界。用户指定了一个精确目标文件时，所有拟写内容必须限定在该文件；除非用户明确要求多文件架构，不得另外创建索引、主题文件或目录。不得把宿主 Agent 自带的自动记忆目录、内部索引格式或当前机器惯例当作用户已经选择的 Memory 架构。指定写入目标不等于批准读取或探测该目标；目录列表、Glob、搜索和存在性检查也属于读取。用户尚未授权读取目标文件或目录时，不得执行这些检查，也不要声称知道其现有格式或是否存在；可以先给只写入该目标文件的保守条目，并把写入前重新读取该目标列为待确认的最小权限。

把用户批准读取的精确路径当作硬白名单，每次读取前都要核对。仅作为写入目标、宿主入口、排除路径或候选路径被点名，都不会把该路径加入读取白名单。在第一次只读提案中，不得试读一个只获写入指定的目标，即使只是为了判断它是否存在；应明确标记“未获授权检查，现状未知”。

### 选择 Memory 模式

- 用户指定一个精确 Memory 文件时，使用单目标模式，不加载或提议共享 preset。
- 用户是全新用户、要求建立一套长期 Memory 体系，或明确要求 Codex 与 Claude Code 共用一份 Memory 时，完整读取 [标准共享 Memory preset](references/shared-memory-preset.md)，再提案。
- 用户已有 Memory 体系时，先在获授权范围内评估，展示保留现状、最小整理或迁入共享 preset 的差异；不默认迁移。

## 3. 对每项发现分类

提出任何写入建议前，将每项发现准确放入一个桶：

| 分类 | 含义 | 默认处理 |
| --- | --- | --- |
| 稳定事实或规则 | 持久偏好、工作规则或路由事实 | 仅在含来源、适用范围、确认或最近审阅日期时，才可作为最小 Memory 的候选 |
| 当前项目状态 | 活跃重点、里程碑或临时决定 | 留在项目中；不得提升为长期 Memory |
| 历史记录 | 已过时或有时效的上下文 | 原地保留；不得作为默认指令 |
| 敏感信息 | 凭据、个人数据、保密客户材料或不明确的私密内容 | 不复制；必要时询问处理方式 |
| 冲突 | 来源对同一持久事实或规则说法不一致 | 展示双方；必须由用户决定 |
| 不导入 | 重复、无依据的推断或不相关材料 | 留在来源中 |

适用于不同范围的事实不一定冲突。标明它们的范围，只有边界仍不明确时才提问。

### 项目路由登记模式

收到 `launch-project` 交付的路由候选，或用户明确要求登记一个项目入口时：

1. 确认候选仍标为未批准，并取得检查稳定入口与目标 Memory 文件所需的最小读取授权。
2. 核对项目正式名称、用户明确提供的别名、项目根路径、稳定入口精确路径、路由信号、适用范围、敏感边界、来源和候选日期。缺失项保持缺失，不猜测。
3. 读取稳定入口只为验证路径、项目身份和声明的 Memory 边界；不得因此读取项目正文或当前状态，也不得把项目动态复制进 Memory。
4. 检查目标 Memory 中的名称冲突、别名冲突、同一路径重复登记、旧路径和范围冲突。冲突未解决时只报告，不写入或指定临时默认。
5. 按目标 Memory 已有格式生成一条最小路由条目。无论格式如何，语义上都必须保留项目名称与别名、根路径与稳定入口、适用范围、来源，以及本次用户确认日期；敏感边界可保留为简短排除说明或指向项目契约。

路由条目只帮助宿主找到项目入口，不保存当前阶段、下一步、阻塞、负责人变化或其他易变项目事实。没有 Workspace Memory 路由时，不承诺仅凭项目名称自动发现项目。

## 4. 先报告，再做任何变更

只读时，返回包含以下部分的简明建议：

1. **已检查的获授权来源**：精确路径及所有排除区域。
2. **保留**：已在正确位置的稳定信息。
3. **候选新增项**：每项都要有来源、适用范围、确认或最近审阅日期及理由；这些追溯字段必须出现在拟写的精确条目中，或明确映射到目标 Memory 已有的对应字段，不能只写在条目外的说明里。
4. **冲突**：两种说法、来源、影响与所需的精确决定。
5. **不导入**：当前状态、历史、敏感材料、重复与无依据推断。
6. **拟议下一次写入**：精确目标路径和精确条目，或“未提议写入”。只列用户已指定或明确同意的目标；不要为了套用宿主 Memory 布局而扩大文件清单。

项目路由登记还必须明确显示：候选来源、检测到的重复或冲突，以及写入后预期形成的“项目名 / 别名 → 稳定入口”关系。不要只说“添加项目路由”而省略条目原文。

绝不悄悄解决冲突。不要建议任一冲突规则成为临时默认，包括看似“更安全”或“更保守”的做法；用户选择或定义范围前，规则均为未解决状态。绝不把当前优先级变成永久规则。用户未批准目标与内容前，不得承诺写入。

## 5. 仅在明确、具体确认后写入

仅在用户同时确认以下两项后继续：

- 精确的目标文件；以及
- 要新增、更新或删除的精确条目。

写入前，先在获授权范围内重新读取目标。只做实现确认所需的最小改动。不要覆盖相邻条目、导入整篇文档，或包含未解决冲突和敏感内容。

对于项目路由，确认必须发生在本 Skill 展示精确条目之后；此前对项目文件、启动方案或路由候选的批准都不能替代。写入时使用实际确认日期，保持项目状态留在项目内，并避免创建同一路径的重复入口。

对于共享 preset，Memory 内容、物理目录与主题文件、双宿主入口、全局宿主规则、已实证需要的宿主读写权限配置和 Git 操作必须分开列出精确变更。一次确认可以覆盖多项，但只限于用户明确点名批准的那些项；对 Memory 内容的批准不自动授权创建软链接、修改全局规则、变更宿主权限或初始化 Git。

之后报告变更的路径、写入的条目及刻意保持未解决的事项。若用户未确认，则保持只读。

## 护栏

- 不要通过复制每个项目或聊天记录来创建全局 Memory。
- 不要把宿主 Agent 的内部自动记忆路径或默认索引布局强加给用户指定的 Memory 目标。
- 不要超出获授权范围扫描。
- 不要复制秘密、个人数据或不明确的保密内容。
- 不要合并、覆盖、二选一或为冲突的 Memory 来源指定临时默认。
- 除非用户明确采纳了持久跨项目规则，否则将项目执行状态留在项目文件中。
- 将项目契约的 Memory 范围视为硬边界：不要提升契约排除在工作区 Memory 或 Portfolio 之外的事实。
- 不要把项目路由候选当作已经确认的 Memory；候选、目标文件与精确条目必须在本 Skill 中重新审阅。
- 不要创建两份 Memory 再用镜像、复制或双写同步；双宿主必须最终指向同一物理库。
- 不要使用强制覆盖软链接、删除既有目标、覆盖全局规则、自动添加 Git 远程或推送。
