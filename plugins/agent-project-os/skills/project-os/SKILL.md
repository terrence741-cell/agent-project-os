# Project OS

降低使用 Agent Project OS 的门槛。这是一个轻量路由器，不是项目管理器：识别用户当下所需，并交给一个工作流。

## 路由请求

依据用户想达成的结果，而不是「项目」等关键词或推断出的项目健康度。意图明确时，只选择一条路径。

| 用户当前意图 | 自然语言信号 | 路由 |
| --- | --- | --- |
| 启动、接手或为一个项目搭起基本框架 | “开始一个项目”“帮我接手”“整理这个项目”“让它能持续做下去” | `launch-project` |
| 推进当前工作或记录一条更新 | “今天做了什么”“接下来怎么办”“更新一下进度”“安排这周”“这是今天的情况” | `project-check-in` |
| 重新考虑方向、范围、节奏或持续存在的阻塞 | “要不要调整方向”“项目卡住了”“复盘一下是否还值得做”“目标可能不对” | 中途审阅工作流 |
| 建立、检查或治理持久的工作区 Memory | “建立记忆”“整理长期偏好”“哪些该记住”“检查 Memory” | `bootstrap-workspace` — Memory 治理路径 |
| 比较多个项目的优先级、冲突或复用机会 | “我有哪些项目”“先做哪个”“项目互相冲突吗”“整体项目复盘” | `review-portfolio` |

不要仅因请求包含「项目」「复盘」或「记忆」就路由。例如，“更新这周的项目进度”进入 `project-check-in`；“这个项目的目标还合适吗”进入中途审阅。

## 选择一个当前 Skill

路由器不是当前执行工作的 Skill。它必须准确选择一条路径，然后退出。读取所选同级 `SKILL.md`，并在同一回复中执行其中第一个适用步骤。

| 路径 | 要加载的 Skill 文件 |
| --- | --- |
| `launch-project` | `../launch-project/SKILL.md` |
| `project-check-in` | `../project-check-in/SKILL.md` |
| 中途审阅工作流 | `../review-project-structure/SKILL.md` — 见下方说明 |
| Memory 治理 | `../bootstrap-workspace/SKILL.md` |
| `review-portfolio` | `../review-portfolio/SKILL.md` |

**中途审阅尚无专用 Skill。** `review-project-structure` 覆盖的是项目如何组织，不判断项目方向、范围或是否仍值得投入。仍将其作为当前最接近的路径，但必须用一句话明确说明：此版本审阅的是项目结构，而非方向，以免用户期待该 Skill 不会给出的判断。不要用结构性答案悄悄替代用户的问题。

本轮只有被选中的 Skill 可以进行实质工作。它的结论、未解决问题和声明的下一步，会成为用户下一条消息的路由上下文。使用这段最近的上下文续接所选工作流，不要将用户重新送回通用路由问题。

## 派发或澄清

### 意图明确时

加载所选 Skill 文件并立即执行。不要单独展示“路由：……”；不要要求用户确认路由、等待“对的”，或让用户改为调用另一个 Skill。

只有在有助理解时，才可用一句简短自然的话引入；随后继续该 Skill 的实际首个回复。例如，明确要启动项目时，应立即得到 `launch-project` 的启动包，而不是路由标签。

### 意图不明确时

只问一个简短问题，其回答能区分可能的路径。不提供诊断、文件计划或额外问题。

当请求宽泛到可能属于两条以上路径时，使用一个紧凑的五路径问题，而不是任意二选一：

> 你现在最想先做哪件事：启动/接手一个项目、推进正在做的工作、重新判断项目方向、整理长期记忆，还是比较多个项目？

示例：

- “你现在是想推进一件正在做的事，还是重新判断这个项目的方向？”
- “你想处理一个具体项目，还是比较多个项目的优先级？”
- “你是想建立长期记忆，还是为一个项目补充今天的最新情况？”

收到回答后，只路由一次。不要在此 Skill 中开始第二轮澄清。

## 边界

- 不要为了选择路径而读取工作区索引、项目文件、Memory 或文件夹。派发时必须读取所选同级 Skill 文件。最近当前对话的结论只能作为续接上下文，不是项目事实的证据。
- 不要创建、更新、移动或删除文件，包括项目状态和 Memory。
- 除了选择路径外，不要评估项目状态、诊断阻塞、总结证据或建议行动。
- 不要把不明确的请求塞进一个兜底路径；请问一个区分性问题。
- 用户可以跳过此路由器，直接调用特定工作流。
